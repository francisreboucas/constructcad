# AGENTS.md

Guidance for AI coding agents working in this repository.

## Commands

```sh
cargo run -p cc_app                                   # app (opens the home screen)
cargo run -p cc_app -- examples/casa_simples.ccad     # open a project
cargo run -p cc_app -- examples/casa_simples.ccad --view "Elevação: Sul" --lang en
cargo run -p cc_core --example casa_simples           # regenerate examples/casa_simples.ccad
cargo run -p cc_cli -- commands                       # the engine's command catalog (no GUI)
cargo run -p cc_cli -- -p examples/casa_simples.ccad run elements_list category=wall
cargo run -p cc_cli -- mcp                            # MCP server over stdio
cargo run -p cc_cli -- reference > docs/commands.md   # regenerate the command reference (a test checks it)

cargo test --workspace                                # all tests
cargo test -p cc_geom rooms                           # tests of one crate matching a name
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all -- --check                            # max_width = 120 (rustfmt.toml)
CC_UI_SNAPSHOTS=1 cargo test -p cc_app snapshots      # compare UI screenshots (tests/snapshots)
UPDATE_SNAPSHOTS=1 cargo test -p cc_app snapshots     # rewrite them after an intended UI change

# IFC validation (CI only; IfcOpenShell is never a build/runtime dependency)
pip install -r scripts/requirements-ifc.txt
cargo run -p cc_ifc --example export_ifc -- examples/casa_simples.ccad out.ifc
python scripts/validate_ifc.py out.ifc
```

CI (`.github/workflows/ci.yml`) runs fmt, clippy + tests on Linux (x86_64 and arm64)/Windows/macOS, the IFC validation job (exports `examples/casa_simples.ccad`, `crates/cc_ifc/tests/fixtures/features.ccad`, `structure.ccad`, `mep.ccad`, `arcs.ccad`, `roofs.ccad` and `phases.ccad`), and a DCO check on PRs: commits must be signed off (`git commit -s`).

## Architecture

Rust workspace (edition 2024). Dependency direction: `cc_core` ← `cc_geom` ← `cc_views` / `cc_render` / `cc_ifc` ← `cc_engine` ← `cc_cli` / `cc_app`, and `cc_core` ← `cc_cad` ← `cc_engine`. `cc_core` knows nothing of geometry, views or UI; no crate depends on `cc_app`.

**Every user-facing operation must be reachable without the GUI**, as a command of `cc_engine`; the GUI, the `ccad` command line and the MCP server call the same commands. A new feature starts as an engine command (with a test in `crates/cc_engine/tests`), and the GUI calls it; do not put model logic in `cc_app`. The app holds a `Session` (`AppState::session`) and changes the model only through commands: `Session::run(SomeCommand { .. })` (typed, the same path as JSON commands), `actions::run_command` (errors to the status bar), or `engine_edit::{element, element_type, view, material, units, info, level, system}`, which turn a change on a copy of an object into its `*_set` command; dragged values pass a merge key (`Session::run_merged`) so they stay one undo step. The only direct document uses left are cancelling a dialog (`Session::undo_to`) and the untracked 3D camera. User documentation: `docs/automation.md` (and `docs/automacao.md`), `docs/interface.md` (and `docs/interface.pt-BR.md`) for the ribbon, tooltips, palette and UI tests; `docs/commands.md` is generated from the catalog (`reference.rs`), every parameter needs a doc comment, and `examples/small_house.ccmacro` is run by a test. Commands run through `Session::execute` are recorded while a macro is recording (edits only; dragged values once); macros are `cc_engine::script` files, the format `ccad script` runs.

- **cc_core** — the BIM model. `Project` (levels, materials, `types: BTreeMap<ElementTypeId, ElementType>`, `elements`, `views`) is the single source of truth. Every edit goes through `Document::edit` / `edit_merged`, which records a reversible `Transaction` (elements, views, types and project "settings" are tracked); continuous edits use `edit_merged` + `break_merge`. `Uid` is a persistent 128-bit id on project/types/elements (used as IFC GlobalId); `Document::new`, `from_ron` and `add_element/add_type` assign missing or duplicated ones. Files are versioned RON (`persist.rs`, `FORMAT_VERSION`): new fields must have serde defaults so older files load; bump the version for semantic changes. Old projects get missing ids and default annotation types on load.
- **Components** — `cc_core::component`: a `TypeData::Component { component, def }` holds a `ComponentDef` (params + pieces); types sharing `component` share the definition and differ in parameter values (the editor applies changes to all of them). Piece fields are `cc_core::expr` expressions (bounded parser, errors as values), except fixed `ComponentShape::Mesh` pieces (imported geometry); a sketched piece's `ProfilePoint`s run straight, along an arc (`radius`) or along part of an ellipse (`ellipse`) to the next point, and `cc_core::profile::from_curves`/`to_curves` turn sketch curves into these vertices and back; `ComponentDef::resolve` returns prisms (mesh pieces also carry their faces) in the component frame plus per-piece errors, and `cc_geom::component_parts` places them in the world (plans draw mesh pieces with `cc_geom::mesh_plan`). `.ccomp` files (`component_file.rs`) are validated on load. Doors and windows are components too (`cc_core::openings`): a `ComponentKind::Door`/`Window` definition with a `HostOpening` (width, height and default sill as expressions; `own_symbol` to draw its in-plan pieces instead of the category's swing or sash lines, `plan_only` pieces being 2D symbols with no solid) makes types of the door or window category, whose `ElementKind::Door/Window(Hosted)` elements cut that opening in their wall; the pieces are resolved with `WallThickness` defined, in a frame centered on the opening (x along the wall, y towards the side the door opens to, z up from the sill), mirrored by the element's flips (`cc_geom::opening_parts`, `ModelGeometry::opening_fills`). `ElementType::opening_size`/`default_sill` read either kind; the template's and IFC-imported door and window types are built-in definitions, and older files' fixed `TypeData::Door/Window` types become them on load (format 12).
- **cc_geom** — derived geometry, rebuilt from scratch by `ModelGeometry::build` whenever the document revision changes. Walls: joins are resolved per level on the body centerline (`Project::wall_axis`, which applies the wall's `LocationLine` and the type's core layers); an arc wall (`Wall::bulge`, see `cc_core::arc`) keeps a concentric centerline, its `WallGeom::arc` maps wall-local `(u, v)` (along the arc, to its left) to the plan, faces meet neighbors at the true crossings of their lines and circles, plans draw arcs as short chords and solids mark their curved facets `Face::smooth` (no seams, silhouettes only); base/top come from `Project::wall_base_z/wall_top_z` (top may be attached to a level). `WallGeom` holds columns between openings; per-wall volume is analytic (the body solid omits caps at joins). `opening_parts` gives the pieces of a door or window (component pieces, or the boxes of `hosted_parts` for old fixed types) shared by the 3D view, plans and IFC. Pitched roofs come from the weighted straight skeleton in `skeleton.rs` (a wavefront simulation with edge and split events: sloped eaves move in at `1 / slope`, gables stay; `Roof::edge_slopes` overrides the slope or makes a gable per outline edge; faces per plane, hips, valleys and ridges; bounded, errors as values, the old lowest-plane construction as fallback), over outlines with openings (`Roof::holes`); `roofs.rs` builds the slab. `rooms.rs` finds a room boundary by tracing the face of the wall-footprint arrangement around the room point. Beams (and strip footings) resolve their ends in `beam.rs`: an end inside a structural column stops at its face, other ends reuse the wall joins (`resolve_join`) among beams at a common depth; `section.rs` turns column and beam sections (rectangular, round, I, U, L, tubes) into non-overlapping parts and outlines; `analytical.rs` builds the analytical model (members between shared nodes) from columns and `ModelGeometry::beams`; `rebar.rs` lays out the bars of each `Rebar` set (an element hosted by a beam or column, removed with it) in its host.
- **cc_views** — views are queries over the model: `generate(project, geom, view)` returns a resolution-independent `Drawing2D` (lines with `LineStyle`, fills, anchored/rotated text in paper mm). Plans (`plan.rs`), projected views (`projected.rs`: elevations, sections, axonometric, painter's algorithm ordered by pairwise depth comparison of overlapping faces), legends, schedules (`schedule.rs`: a `ScheduleDef` in the view picks fields, sort, filter and totals; headers and some cells are i18n keys; `to_csv`), sheets (`sheet.rs`: `compose_sheet` lays out border, title block and scaled viewports in paper mm; the app paints it and `export.rs` writes it as SVG, a hand-written PDF with standard Helvetica, or PNG through resvg with text drawn as Inter outlines by `skrifa`; `view_on_paper` lays out any view the same way for `view_export`) and annotations (`annotate.rs`: room/door/window tags, grids, dimensions). Dimensions store points in the view's own drawing coordinates, so they work in any 2D view; in plans, elevations and sections each end may also reference a point of an element in its own frame (plus a height from its base or top in elevations/sections, through `View::projection`) or a level (`cc_core::dim_refs`), and every edit ends by moving referenced ends inside the same transaction (`EditCtx::finish` → `sync_dimensions`), so dimensions follow their elements and undo with them. A fill with alpha 0 is not hit-testable and only shows when its element is highlighted (room areas).
- **MEP** — `cc_core::mep`: plumbing systems and electrical circuits (`MepSystem`, kind, code, color, board, voltage) live in `Project::systems` (tracked as settings); pipes and conduits are `ElementKind::Pipe/Conduit(MepSegment)` runs with an elevation at each end and the systems they belong to; plumbing fixtures and electrical devices are components whose `ComponentDef::mep` holds fixture units or the device kind and power, connected by `Component::system`; a component's `ComponentDef::connectors` (name, system kind, position and direction expressions, diameter) are where runs join it (`cc_geom::component_connectors`): the network attaches each to a node of a system of its kind, and `mep_connect` starts branches there (components without connectors use their insertion point). `cc_geom::mep` makes the cylinders (`ModelGeometry::segments`) and `cc_geom::mep_net` the networks (`ModelGeometry::mep`: nodes where runs meet, edges, derived fittings, fixtures and devices attached to nodes), `cc_geom::sizing` sizes pipes and circuits from them, `cc_views::mep` draws plumbing and electrical plans (`ViewKind::FloorPlan { mep: Some(..) }`, the architecture faded; other floor plans leave MEP out) and the device symbols, `cc_views::diagram` the panel diagrams (`ViewKind::Diagram`, headings through the `label` of `generate_labeled`), `cc_engine::commands::mep` holds the commands and the circuit loads.
- **cc_render** — offscreen wgpu renderer for 3D views (`Renderer3D`); `render_to_rgba` reads a frame back (home screen thumbnails).
- **cc_ifc** — IFC4 export with an in-house STEP writer (`step.rs`) and IFC2X3/IFC4 import with an in-house STEP parser (`parse.rs`, bounded nesting), geometry engine (`geometry.rs`: placements, curves, profiles, swept/CSG/B-rep/face-set items → world polygon meshes, depth- and size-bounded) and mapping (`import.rs`); no third-party IFC libraries by design. Import never drops a physical class: products become native elements only when a native element holds their geometry exactly (types matched by name and size; GlobalIds kept as `Uid`s), slabs become floors (with `Floor::openings` from profile voids and from openings that pass through them vertically) or, as base slabs shaped like slabs, foundation slabs (piles and pile caps written as base slabs stay components); anything else (including coverings, roofs, columns and beams voided by openings) becomes a component with `Mesh` pieces whose `ComponentDef::ifc` keeps the class and the type's property sets (`cc_core::properties`, values in SI units; instance sets live in `Component::properties`), with its openings subtracted by `csg.rs` (arena BSP-tree booleans, iterative and budgeted; also used for boolean results); `schema.rs` (IFC4 attribute layouts and type objects per element class) lets export write that class back. `tests/round_trip.rs` checks export → import. GlobalIds come from `Uid`s; derived objects (relationships, openings) hash the project uid with a tag.
- **Imported CAD drawings** — `cc_core::cad` holds the neutral drawing (`CadDrawing`: layers with RGB colors and file visibility, flat `CadPrim`s in drawing units — polylines with bulges, arcs kept as arcs, single-line texts with alignment, fills — extents and declared units) and the element `ElementKind::CadImport(CadImport)` (category `CadImport`, a `TypeData::CadImport {}` type created with the first import): owned by one view (`view`, like text notes; plans, ceiling plans, elevations, sections and legends, see `cc_views::hosts_cad`) and placed by `units`, `scale`, `position`, `rotation_deg` and `mirrored`, with `hidden_layers`, `color_mode` and `halftone`. The drawing is an `Arc` so undo steps and the repair check do not copy it; `repair` drops invalid primitives (copying only when needed), and the element has no phase. **cc_cad** reads files into it: an in-house DXF reader (`tokens.rs` ASCII/binary group pairs and code pages, `dxf.rs` sections/LAYER table/BLOCKS/ENTITIES, model space flattened while read, `flatten.rs` OCS → world with the arbitrary axis algorithm, nested/arrayed inserts with a cycle guard, depth, primitive and work budgets, layer 0 and BYBLOCK inheritance, `geom.rs` ellipses and de Boor splines, `text.rs` MTEXT codes); DWG goes through the `acadrust` crate (no default features, read from a byte buffer) on its own thread inside `catch_unwind`, its document written to binary DXF in memory and read by the same reader. `cc_views::cad` draws an import in its view under everything (thin lines with their own `Pen`, tessellated for the view scale), and `Drawing2D::background` makes `hit_test` pick it only where nothing else is; `graphics::apply` merges overrides into a line's own pen. `cc_engine::commands::cad` holds `cad_import`, `cad_layers` and `cad_layers_set`; `element_get`/`element_set` show and patch the placement without the drawing (`cc_engine::element_params`). The app's tools snap to `CadImport::snap_features` (ends, midpoints, centers, lines, arcs) of the active view's imports; IFC export and 3D views ignore them.
- **cc_engine** — the engine: a `Session` (the `Document` plus cached geometry, drawings and sheets) and a catalog of commands (`registry.rs`). A command is a parameter struct (`Deserialize` + `schemars::JsonSchema`; its doc comment is the description, its fields' doc comments the parameter docs) implementing `Command { NAME, KIND, run }`; register it in `registry!`. Names are `snake_case` (valid MCP/model tool names). Edits go through `commands::edit`, i.e. `Document::try_edit` + a repair check, so a command that would leave the model invalid is refused without an undo step. Levels, types, views and materials resolve by id or name (`refs.rs`); lengths in meters, angles in degrees, points `[x, y]`. `*_get` queries show the `params` that `*_set` commands merge (JSON merge patch over the model's serde form). Errors are values (`EngineError { code, message }`); `Session::execute` guards panics. Creation defaults shared with the drawing tools live in `defaults.rs`; localization (`i18n.rs`, the `t!` macro) lives here too and `cc_app::i18n` re-exports it.
- **Roof coverings and framing** — `cc_core::roofing`: `TypeData::Roof { covering, framing }` (serde defaults): a `TileKind` from the built-in catalog (`TileKind::spec`: least slope, weight, tiles per m², batten gauge, purlin span) and a `RoofFraming` (system None/Timber/TimberTrusses/Steel, material, purlin/rafter/batten `MemberSize`s and spacings, repaired on load). `cc_geom::roof_framing` frames each sloped underside plane of the roof's built solid, coplanar pieces together (battens at the gauge, rafters down the slope, purlins spread evenly; trusses: also king-post trusses across the eave direction of the largest face, cut from the faces sloping across them moved under the purlins, chords met at the apex, chords apart making separate trusses; steel: purlins only), as boxes across the roof plane; `build_slabs` stores it in `ModelGeometry::roof_framing` and adds the members as a `Category::Beam` solid of the roof element marked `Solid::secondary`: drawn, but left out of `ModelGeometry::body_of` (volume, joins, plan edges, IFC body), and section cuts hatch it in the framing's material. The covering's rules (`TileSpec::accepts`, `tiles`, `weight_on`) are shared by the check, properties and schedules; `type_set` gives a new covering the framing it usually lies on when none was chosen. `roof_check` and `element_get`'s `roofing` give the slope against the covering's least, tiles, weight and framing figures; schedules have `TileCount`, `FramingLength`, `FramingVolume`, and `Slope`/`Weight` for roofs.
- **Sketches** — `cc_core::sketch`: a `Sketch` is the `SketchCurve`s (lines, bulge arcs, circles, whole or partial ellipses) an outline was drawn with; `Sketch::profile` chains them into loops (ends within `JOIN_TOL`, bounded, arcs and ellipses split every `ARC_STEP`) and returns the outline and its openings, or a `SketchError` with the point (open end, branch, crossing, apart, nested, openings where none are allowed). Floors, ceilings, roofs and masses keep theirs in an optional `sketch` field (`Element::drawn_sketch`, `sketched_profile`); `Element::transform`/`translate` move it, and `EditCtx::finish` (`sync_sketches`) and `repair` drop one that no longer makes the outline (`Sketch::makes`), so editing the points directly leaves the curves behind. `cc_engine::commands::sketch`: `CurveArg` (also rectangles and polygons, as lines) is the `curves` argument of `floor_create`, `ceiling_create`, `roof_create`, `foundation_slab_create` (outline only, not kept) and `mass_create`; `sketch_get` and `sketch_set` read and redraw an outline. In the app, `sketch_mode` holds the open sketch (`AppState::sketch`, opened by `set_tool` with a `Tool::Sketch`, or by *Edit Boundary*): its own ribbon (drawing tools, *Finish*/*Cancel*), the canvas (preview, snapping to the sketch's points, picking, grips that move joined ends together), the picked curve in the properties palette and its own undo, window and chain selection, and the Modify tools (move, copy, rotate, mirror, offset, trim/extend, split: the same `UiCommand`s, routed to the sketch while one is open, the geometry in `cc_core::sketch_edit`); *Finish* runs the creation command with `curves` or `sketch_set`.
- **Conceptual masses** — `cc_core::mass`: `ElementKind::Mass(Mass)` (category `Mass`, a `TypeData::Mass { material }` type created with the first mass) is a base `outline` extruded `height` up from its level plus `base_offset`, or lofted to a `top` outline (`cc_core::sweep::blend`; outlines with as many points join vertex to vertex, so an inset is exact), with `floors`, the levels where mass floors are taken. `cc_geom::mass` builds the see-through body and the mass floors (`Mass::section` at each listed level the mass spans, with area and perimeter; `ModelGeometry::masses`); plans draw a mass where it stands or is cut (`draw_mesh`) with the floor of their level and its area; schedules have `FloorArea` and `FloorCount`. `cc_engine::commands::mass` holds `mass_create` (with `top` or `top_inset` for a loft), `mass_floors_set`, `mass_floors` and `mass_type_create`; deleting a level drops its mass floors. `mass_walls_create`, `mass_slabs_create` and `mass_roof_create` build walls (exterior face on the mass, `LocationLine::FinishExterior`, outline run clockwise), floors on the mass floors and a flat roof from a mass. IFC export leaves masses out, like imported drawings.
- **Phases** — `cc_core::phase`: `Project::phases` (time order), `phase_filters` and `phase_graphics` are tracked as settings; each element has `phase_created` (`PhaseId(0)` = unassigned, read as the last phase) and `phase_demolished`, each view a `phase` and `phase_filter` (templates control the filter only). `Project::phase_state` gives an element's status in a view's phase (existing, demolished, new, temporary, or absent); `cc_views::graphics::PhaseView` turns it into visibility and overrides inside the `Resolver` (phase overrides rank between view filters and the category). `EditCtx::finish` gives elements and views added by an edit the creation phase (`Document::creation_phase`, the active view's) and applies `Project::phase_fixes` (hosted elements follow their hosts); `repair` resets bad references and files before version 11 get the template's phases (`ensure_phases`). Rooms are bounded by the walls standing at the end of their creation phase (`ModelGeometry::build_rooms`), and a view whose phase leaves elements out uses `ModelGeometry::build_phase` (cached per phase in `Session::view_geometry`), so later doors do not open existing walls and walls join only within the phase. IFC export writes the status relative to the last phase as the common property sets' `Status` plus the phase names (`ConstructCAD_Phasing`, `ConstructCAD_Phases`); import reads them back.
- **Dimensions** — `cc_engine::dimensions`: `associate` ties the ends of a new dimension to the elements or level lines whose linework in the view passes through them; `set_value` drives the model from a new value (commands `dimension_create`, `dimension_set_value`).
- **View graphics** — `cc_core::graphics`: each `View` has `graphics` (category visibility and overrides, applied `FilterUse`s in order, element overrides, hidden elements) and an optional `template`; `Project::filters` (`ViewFilter`: categories plus rules on a `ScheduleField` or the level elevation) and `Project::templates` (`ViewTemplate`, with an `include` flag per property) are tracked as settings. `EditCtx::finish` → `sync_views` copies each template's included properties into the views that follow it and drops references to deleted elements, filters and templates, so propagation is part of the same undo step. `cc_views::graphics` resolves an element's graphics (`Resolver`: element override, then the first matching filter, then the category, attribute by attribute) and applies them to the generated `Drawing2D` (lines carry a `Pen`, fills know whether they are `cut`, material hatch lines are `LineStyle::Hatch`, texts carry their element); `cc_render::SceneMesh::build` takes a per-element `SolidStyle`. Temporary hide/isolate is session state (`Session::set_temporary`), not model state: `Session::drawing` applies it, sheets and exports use `printed_drawing`.
- **cc_cli** — the `ccad` binary (no egui/wgpu): `commands`, `schema`, `reference`, `run` (JSON, `@file`, `-` or `key=value` arguments), `script` (JSON array or lines; stops at the first error), `mcp` (an in-house MCP server: JSON-RPC 2.0 over stdio, every command a tool with its schema; `mcp.rs`). Options `-p` (open `.ccad` or import `.ifc`), `--save`, `--save-as`, `--lang`.
- **cc_app** — eframe/egui app. `cad_ui.rs` holds Import CAD (file dialog and dropped files) and the properties and layers of an imported drawing. `AppState` (state.rs) holds the `Document`, cached geometry/drawings, selection, active `Tool`, dialog flags. `app.rs` lays out the quick access toolbar + ribbon, options bar, left panel (project browser over properties), the egui_dock view tabs, and the home screen (`home.rs`) when `show_home`. Tools (`tools.rs`) run inside 2D canvases; `preferences.rs` holds the app preferences (`AppState::prefs`: theme, interface scale and text size, ribbon, tooltips, library/macros/projects folders, autosave, recent count), every eframe storage key with their validated load/save, `sync_look` (applies theme, zoom and font scale each frame) and the Preferences window (Ctrl+,; Cancel restores a snapshot); `library.rs` is the component library window (the `.ccomp` files of `Preferences::library_folders`, edited in Preferences → File locations, listed by `component_library_list`); `phases_dialog.rs` holds the Phases dialog, the phase rows of view and element properties and the Demolish tool, and `AppState::sync` sets the creation phase to the active view's (`phase_creation_set`); two-letter shortcuts are matched in `app.rs::shortcuts`.

## UI conventions

- **Familiar by design**: menus, shortcuts, panels and tools go where desktop CAD/BIM users expect them (quick access toolbar top-left, ribbon tabs, properties/browser docked left, standard Ctrl shortcuts and two-letter tool keys). Use general conventions only — never a specific product's icons, colors or wording; prefer neutral terms (Category, Type, Component — not "Family").
- Colors and fonts come from `theme.rs` (`LIGHT` and `DARK` hold the tokens; `PALETTE` reads those of the theme shown, which `theme::sync` follows every frame, and `theme::palette(ctx)` picks by the egui theme; the user picks light, dark or the system's with `ThemeChoice` in the Preferences window, and a text size (`theme::set_font_scale`) that scales the text styles and the property tables; 2D drawings keep white `paper` in both; Inter). Icons are our own SVG line drawings in `assets/icons/ui` (24 grid, white strokes, `stroke-width` 1.75, round caps/joins, soft fills at 20% opacity), rasterized by resvg per pixel size in two layers and tinted in `icons.rs`: strokes in the ink tone, soft fills in the tint tone (`icons::Tones`), plus an optional badge (new, import, export, remove).
- Ribbon, quick access and shortcut entries are `commands::UiCommand`s: label, shortcut, description, engine command and availability (with the reason) are defined there once; buttons and tooltips read them. Custom widgets report their role, label and state with `Response::widget_info`, so `ui_tests.rs` (egui_kittest) can find them by label; screenshot references live in `crates/cc_app/tests/snapshots` and run on request, since GPUs render slightly differently.
- Every modal uses `dialog::Dialog` (header with close button, footer buttons right-aligned: main action first, Cancel last; auxiliary buttons left; `danger` for destructive). Dialogs that edit data offer OK/Cancel and wrap edits in `dialog::session` so Cancel undoes them.
- Property grids use the shared `table.rs` primitives (collapsible `section`, two-column `row`).
- No hard-coded interface text: keys live in `assets/i18n/*.ftl` (`pt-BR` is the reference, then `en`, `es`, `fr`, `de`, `it`, `lo`, `pl`, `uk-UA`, `zh-TW`, `zh-CN`), read with `t!` / `tr`. A test scans the sources and fails if any key used in code is missing from a language, and another fails unless every language has the same keys and placeholders, so add every new key to all of them.

## Robustness rules

- **Non-test code never panics.** No `unwrap()`, `expect()`, `panic!`, `unreachable!`, `todo!`, `unimplemented!` — the workspace denies them in clippy (`[workspace.lints]`), and `clippy.toml` allows them only in tests. Return errors and propagate with `?`, or use `let … else`, `if let`, `ok_or(…)?`, `unwrap_or*` where the fallback is truly correct (never one that silently corrupts a document).
- **No `unsafe`** (`unsafe_code = "forbid"`).
- **Files are hostile input.** `.ccad` files pass through `Project::repair` on load (`persist::from_ron_with_repairs`): invalid numbers and dangling references are removed or reset and the app reports how many. Use `get()` for indices that come from files, selections or arithmetic on them; guard divisions by zero and NaN/inf.
- **Bound recursion and loops** over model references with visited sets or limits (hosting can be cyclic in a crafted file; see `EditCtx::remove_element`).
- **Last-resort guard:** opening, saving and exporting run inside `actions::guard` (`catch_unwind`); a panic becomes an error message and the open document is kept. Keep `panic = "unwind"` (the default profile).
- **Prove it:** every crash fix comes with a small synthetic regression test that failed before the fix.

## Project policies

- Clean-room: behaviour comes from public documentation, general CAD conventions, open standards and user feedback; reference tests use analytic values or open-source tools (see CONTRIBUTING.md and the README "Independence" section).
- Code, comments, identifiers and commit messages are in English; the user communicates in Portuguese.
